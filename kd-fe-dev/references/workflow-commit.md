# 代码提交流程

## 1. 确定范围

执行`git status`查看当前工作区的待提交、未跟踪的文件

确认需要提交的文件列表，根据`.gitignore` 排除不应该提交的文件

## 2. 代码审查

对第1步确定的文件中的代码进行审查（code review），检查以下内容：

- 注释代码中的 `console` 相关的语句
- 规范检查：是否符合项目代码规范（命名、格式、结构等）
- 功能完整性：代码逻辑是否正确，功能是否完整
- 潜在问题：是否存在 bug、性能问题、安全隐患
- 注释和文档：关键逻辑是否有必要注释

## 3. 修复问题（如需要）

如果代码审查发现问题，需要：

- 指出具体的问题位置和原因
- 提供修复建议或直接修复代码
- 修复后重新执行第2步进行审查，直到代码符合要求

## 4. 检查当前分支

执行`git branch`或`git status`确认当前所在分支

确保在正确的分支上进行提交（避免误提交到主分支）

## 5. 暂存文件

根据审查结果，暂存需要提交的文件：

```bash
# 暂存所有修改的文件
git add .

# 或暂存指定文件
git add <文件路径>
```

暂存后再次执行`git status`确认暂存的文件列表是否正确

## 6. 编写提交信息

根据 Commitlint 规范编写提交信息，格式为：

```
<type>(<scope>): <subject>
```

**type（类型）**：
- `feat`: 新功能
- `fix`: 修复问题
- `docs`: 文档更新
- `style`: 代码格式调整（不影响功能）
- `refactor`: 代码重构
- `perf`: 性能优化
- `test`: 测试相关
- `chore`: 构建/工具链相关
- `revert`: 回滚提交

**scope（范围）**：
- 客户分支名：如 `zhonghangxin`、`xxx-client`
- 版本号：如 `2.2.9.0`、`2.2.9`、`2.2.9.0+`（标品）
- 模块名：如 `user`、`order`
- 如果影响范围不明确，可以省略

**subject（主题）**：
- 简洁描述本次提交的内容
- 使用中文或英文，保持一致性
- 不超过 50 个字符

**示例**：
```
feat(zhonghangxin): 新增用户管理页面
fix(2.2.9.0): 修复表格分页问题
refactor(user): 优化用户信息获取逻辑
docs: 更新 API 文档
```

## 7. 提交代码

使用编写好的提交信息执行提交：

```bash
git commit -m "<提交信息>"
```

提交时会自动触发 Husky hooks：
- `pre-commit`: 执行代码检查（ESLint、Stylelint、lint-staged）
- `commit-msg`: 验证提交信息格式

如果检查失败，需要：
- 修复代码问题后重新暂存和提交
- 或修正提交信息格式后重新提交

## 8. 推送到远程

确认提交成功后，推送到远程仓库：

```bash
# 推送到当前分支
git push

# 或指定远程和分支
git push origin <分支名>
```

如果远程分支不存在，使用：

```bash
git push -u origin <分支名>
```

## 9. 处理冲突（如需要）

如果推送时出现冲突：

1. 先拉取远程最新代码：`git pull origin <分支名>`
2. 解决冲突文件中的冲突标记
3. 暂存解决后的文件：`git add <文件路径>`
4. 完成合并：`git commit`（使用默认合并信息）
5. 重新推送：`git push`

## 注意事项

- **提交前务必审查代码**：避免提交有问题的代码
- **提交信息要清晰**：方便后续查找和理解提交历史
- **小步提交**：每次提交只包含一个逻辑变更，便于回滚和审查
- **不要提交敏感信息**：如密码、密钥、个人隐私等
- **不要提交临时文件**：如 `.log`、`.tmp`、`node_modules` 等
- **遵循分支管理规范**：在功能分支开发，通过 Merge Request 合并到主分支
